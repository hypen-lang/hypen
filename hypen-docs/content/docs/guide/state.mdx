# State & Modules

Modules are stateful components that manage their own state and handle actions. They are the building blocks for creating interactive, data-driven UI in Hypen.

## What is a Module?

A module combines:
- **State**: Reactive data that the UI depends on
- **Actions**: Functions that modify state in response to user interactions
- **Template**: The Hypen UI definition that renders the state

The key difference between a module and a regular component is that a module's state persists as long as the module exists, and it can respond to actions that modify that state.

## Defining a Module

A module is two files side by side in its own folder. This is the layout `hypen init` creates and `hypen dev` / `hypen build` discover:

```
src/components/Counter/
├── component.hypen   # the UI template
└── component.ts      # state and actions
```

### The UI Template

In `src/components/Counter/component.hypen`, define the module's UI:

```hypen
module Counter {
    Column {
        Text("Count: @{state.count}")
            .fontSize(32)
            .fontWeight("bold")

        Row {
            Button { Text("-") }
                .onClick(@actions.decrement)
                .backgroundColor("#EF4444")
                .padding(16)
                .borderRadius(8)

            Spacer()

            Button { Text("+") }
                .onClick(@actions.increment)
                .backgroundColor("#22C55E")
                .padding(16)
                .borderRadius(8)
        }
        .gap(24)
    }
    .padding(32)
    .horizontalAlignment("center")
}
```

### The Module Definition (TypeScript)

Define the module's state and actions in `src/components/Counter/component.ts`:

```typescript
// src/components/Counter/component.ts
import { app } from "@hypen-space/core";

interface CounterState {
  count: number;
}

export default app
  // Register the module under the name the templates use: Counter()
  .module("Counter")
  .defineState<CounterState>({ count: 0 })

  // Lifecycle handler: receives (state, context?)
  .onCreated(async (state, context) => {
    console.log("Counter module created");
  })

  // Action handler: receives one object { action, state, context, dataSources }
  .onAction("increment", async ({ state }) => {
    state.count++;
  })

  .onAction("decrement", async ({ state }) => {
    state.count--;
  })

  // Lifecycle handler: receives (state, context?)
  .onDestroyed((state, context) => {
    console.log("Counter module destroyed");
  })

  // Terminal call: finishes the definition. The template comes from the
  // sibling component.hypen file.
  .build();
```

<Callout type="info">
Every module definition ends in exactly one terminal call:

- `.build()` when the template lives in a sibling `.hypen` file (as above), or for a module with no template.
- `.ui(template)` / `.uiFile(path)` when the template is inline or in a file you name. These already return the built definition; a trailing `.build()` after them is allowed but does nothing.

Start every module that another template renders (`Counter()`, `Home()`, ...) with `app.module("Name")`, using the same name as its folder and its `module Name { ... }` block. Without the name, `hypen dev` still renders the module's state, but its `@actions.*` are rejected with `invalid scoped UI action`. The entry module (`App` in the scaffold) can use a plain `app.defineState(...)`.
</Callout>

## State

### Defining State

State is defined using `defineState<T>(initialValue)`:

```typescript
import { app } from "@hypen-space/core";

interface UserState {
  user: {
    name: string;
    email: string;
  } | null;
  isLoading: boolean;
  error: string | null;
}

export default app
  .defineState<UserState>({
    user: null,
    isLoading: false,
    error: null
  })
  .build();
```

### Accessing State in Templates

Use the `@{state.path}` syntax to bind state values to your UI:

```hypen
module Profile {
    Column {
        // Simple binding
        Text("Welcome, @{state.user.name}!")

        // Nested paths
        Text("Email: @{state.user.email}")

        // In string interpolation
        Text("Status: @{state.isLoading ? 'Loading...' : 'Ready'}")
    }
}
```

### Two-Way Binding with `.bind()`

For form inputs, use `.bind()` to create two-way data binding — the input value stays in sync with state without any action handlers:

```hypen
module Settings {
    Column {
        Input(placeholder: "Username").bind(@state.username)
        Checkbox {}.bind(@state.notifications)
        Switch {}.bind(@state.darkMode)
        Select {}.bind(@state.language)
    }
}
```

```typescript
import { app } from "@hypen-space/core";

export default app
  .defineState({
    username: "",
    notifications: true,
    darkMode: false,
    language: "en"
  })
  // No action handlers needed for these inputs!
  // .bind() automatically updates state when the user types or toggles.
  .build();
```

When you need additional logic (validation, side effects), use manual event handlers instead of `.bind()`:

```hypen
Input(placeholder: "Email")
    .value(@state.email)
    .onInput(@actions.validateEmail)
```

See the [Inputs guide](/docs/guide/inputs) for complete details on `.bind()`.

### State Updates

State is automatically tracked through a Proxy. Mutate the state object and changes sync automatically:

```typescript
.onAction<{ name: string; email: string }>("updateProfile", async ({ action, state }) => {
  state.user = {
    name: action.payload!.name,
    email: action.payload!.email
  };
  // State changes auto-sync - triggers re-render with new state
})
```

## Actions

Actions are functions that respond to user interactions and modify state.

### Defining Actions

```typescript
// Action handler receives a context object with all parameters
// Use a generic type parameter to type the payload
.onAction<PayloadType>("actionName", async ({ action, state, context }) => {
  // action - contains name, payload (typed as PayloadType), sender
  // state - current state (mutable, auto-synced via Proxy)
  // context - GlobalContext for cross-module communication
  // context.router - HypenRouter for programmatic navigation
})
```

### Dispatching Actions from UI

Use `@actions.actionName` via event applicators in your templates:

```hypen
// Simple action
Button { Text("Save") }
    .onClick(@actions.save)

// Action with payload
Button { Text("Delete") }
    .onClick(@actions.deleteItem, itemId: @state.selectedId)
```

### Action Payloads

Actions automatically receive payload data from the event and any additional arguments:

```typescript
.onAction<{ itemId: string }>("deleteItem", async ({ action, state }) => {
  const itemId = action.payload!.itemId;
  state.items = state.items.filter(item => item.id !== itemId);
})
```

### Async Actions

Actions support async operations like network requests:

```typescript
.onAction<{ userId: string }>("fetchUser", async ({ action, state }) => {
  state.isLoading = true;
  // State changes sync automatically, showing loading state

  try {
    // Modules run on the server, so there is no page origin to resolve a
    // relative URL against: always fetch an absolute URL.
    const response = await fetch(`https://api.example.com/users/${action.payload!.userId}`);
    const user = await response.json();
    state.user = user;
    state.error = null;
  } catch (error) {
    state.error = "Failed to fetch user";
    state.user = null;
  } finally {
    state.isLoading = false;
    // Final state syncs automatically
  }
})
```

### Where Module Code Runs

Module code (`component.ts`, `.onAction`, `.onCreated`, ...) never runs in the browser page:

- Under `hypen dev` and `RemoteServer`, it runs **on the server** (Bun or Node), and the browser only receives patches.
- In the static site that `hypen build` produces, it runs in a **Web Worker**.

Either way there is no `window`, `document` or `localStorage`, and a relative `fetch("/api/...")` has no page origin to resolve against. Use the server-safe equivalents instead:

| Instead of | Use |
|------------|-----|
| `localStorage` / `sessionStorage` | `.persist(store)` with a server-side store. See [State Persistence](/docs/guide/persistence). |
| `fetch("/api/users")` | `fetch("https://api.example.com/users")`, an absolute URL |
| `window.location` / `history` | Router state (`state.location`) and `@router.push`. See [Routing](/docs/guide/routing). |

Timers, `fetch` with absolute URLs and `crypto` work as usual in both places.

## Lifecycle

Modules have lifecycle hooks for setup and cleanup.

### onCreated

Called when the module is first mounted. Receives `(state, context?)`:

```typescript
.onCreated(async (state, context) => {
  // Load initial data. This runs on the server: use an absolute URL,
  // not localStorage or a relative fetch.
  const response = await fetch("https://api.example.com/settings");
  state.settings = await response.json();
  // State changes sync automatically
})
```

### onDestroyed

Called when the module is unmounted. Receives `(state, context?)`:

```typescript
.onDestroyed((state, context) => {
  // Cleanup subscriptions, timers, etc.
  clearInterval(state.timerId);
})
```

## Complete Example: Todo List

### Template (`src/components/TodoList/component.hypen`)

```hypen
module TodoList {
    Column {
        Text("Todo List")
            .fontSize(24)
            .fontWeight("bold")

        Row {
            Input(placeholder: "Add a new todo...")
                .bind(@state.newTodo)
                .onKey(@actions.addTodo)
                .weight(1)
                .padding(12)
                .borderRadius(8)

            Button { Text("Add") }
                .onClick(@actions.addTodo)
                .backgroundColor("#3B82F6")
                .padding(horizontal: 16, vertical: 12)
                .borderRadius(8)
        }
        .gap(12)

        List {
            ForEach(items: @state.todos, key: "id") {
                Row {
                    Text("@{item.text}")
                        .textDecoration("@{item.completed ? 'line-through' : 'none'}")
                        .weight(1)
                        .onClick(@actions.toggleTodo, id: @item.id)

                    Button { Text("✕") }
                        .onClick(@actions.deleteTodo, id: @item.id)
                        .backgroundColor("transparent")
                }
                .padding(12)
                .borderRadius(8)
                .verticalAlignment("center")
            }
        }
        .marginTop(16)
    }
    .padding(24)
    .maxWidth(600)
}
```

### Module (`src/components/TodoList/component.ts`)

```typescript
import { app, type StateStore } from "@hypen-space/core";

interface Todo {
  id: string;
  text: string;
  completed: boolean;
}

interface TodoState {
  todos: Todo[];
  newTodo: string;
  filter: "all" | "active" | "completed";
}

// Modules run on the server, so there is no localStorage. Persist through a
// StateStore instead. This in-memory one keeps one list per browser session
// until the server restarts; swap it for Redis, a database or a file.
const saved = new Map<string, TodoState>();
const todoStore: StateStore<TodoState> = {
  resolveKey: (_state, moduleName, sessionId) => `${moduleName}:${sessionId}`,
  load: async (key) => saved.get(key) ?? null,
  save: async (key, state) => { saved.set(key, state); },
  delete: async (key) => { saved.delete(key); },
};

export default app
  .module("TodoList")
  .defineState<TodoState>({
    todos: [],
    newTodo: "",
    filter: "all"
  })

  // Restores the saved list before onCreated runs, and saves after every change
  .persist(todoStore)

  // No "updateNewTodo" handler needed — .bind() handles it automatically

  .onAction("addTodo", async ({ state }) => {
    if (state.newTodo.trim()) {
      state.todos.push({
        id: Date.now().toString(),
        text: state.newTodo.trim(),
        completed: false
      });
      state.newTodo = "";
    }
  })

  .onAction<{ id: string }>("toggleTodo", async ({ action, state }) => {
    const todo = state.todos.find(t => t.id === action.payload!.id);
    if (todo) {
      todo.completed = !todo.completed;
    }
  })

  .onAction<{ id: string }>("deleteTodo", async ({ action, state }) => {
    state.todos = state.todos.filter(t => t.id !== action.payload!.id);
  })

  .build();
```

## Best Practices

### State Changes Sync Automatically

State mutations are tracked via Proxy and sync automatically:

```typescript
.onAction<{ value: string }>("update", async ({ action, state }) => {
  state.value = action.payload!.value;
  // Changes sync automatically - no callback needed
})
```

### Handle Async Operations Properly

Show loading states and handle errors:

```typescript
.onAction("loadData", async ({ state }) => {
  state.isLoading = true;
  state.error = null;
  // Loading state syncs automatically

  try {
    const data = await fetchData();
    state.data = data;
  } catch (e) {
    state.error = "Failed to load data";
  } finally {
    state.isLoading = false;
    // Final state syncs automatically
  }
})
```

### Use Descriptive Action Names

Name actions by what they do, not how they're triggered:

```typescript
// Good
.onAction("saveDocument", ...)
.onAction("toggleDarkMode", ...)

// Avoid
.onAction("handleClick", ...)
.onAction("buttonPressed", ...)
```

## Platform Support

Modules work identically across all platforms:

- **Web**: the browser renders patches with the DOM or Canvas renderer. Module code runs on the server (`hypen dev`, `RemoteServer`) or in a Web Worker (`hypen build`).
- **Android**: native Compose rendering
- **iOS**: native rendering

The same module definition works on all platforms, with platform-specific rendering handled automatically by the Hypen runtime.
