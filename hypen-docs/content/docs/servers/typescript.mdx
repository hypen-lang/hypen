# TypeScript SDK

The TypeScript SDK (`@hypen-space/core` + `@hypen-space/server`) is the primary way to build Hypen applications. `@hypen-space/core` provides the module system and reactive state management. `@hypen-space/server` provides the WASM engine, component discovery, and the remote server for streaming UI to any client.

## Installation

```bash
bun add @hypen-space/core @hypen-space/server
```

`RemoteServer.listen()` runs on [Bun](https://bun.sh) (it is built on `Bun.serve`), so install Bun 1.x first. You can add the packages with npm or pnpm as well, but run the server with `bun`.

For web client rendering, also install the web adapter:

```bash
bun add @hypen-space/web
```

## Quick Start

Create a server that streams a counter UI over WebSocket:

```typescript
import { HypenApp } from "@hypen-space/core";
import { RemoteServer } from "@hypen-space/server";

// 1. Create an app registry and define modules on it.
const myApp = new HypenApp();

myApp.module("Counter")
  .defineState({ count: 0 })
  .onAction("increment", ({ state }) => { state.count++; })
  .onAction("decrement", ({ state }) => { state.count--; })
  .ui(`
    Column {
      Text("Count: @{state.count}")
        .fontSize(32)
        .fontWeight("bold")

      Row {
        Button { Text("-") }
          .onClick(@actions.decrement)
          .padding(16)

        Button { Text("+") }
          .onClick(@actions.increment)
          .padding(16)
      }
      .gap(16)
    }
    .padding(32)
  `);

// 2. Serve the app. With no .module() call, the entry is the module
//    named "App" if there is one, otherwise the app's only module.
await new RemoteServer()
  .app(myApp)
  .onConnection((client) => console.log(`Connected: ${client.id}`))
  .onDisconnection((client) => console.log(`Disconnected: ${client.id}`))
  .listen(3000);
```

`.ui(template)` finishes the module definition, so no `.build()` is needed after it (a trailing `.build()` is allowed and does nothing). Modules without an inline template end with `.build()` instead.

Run it:

```bash
bun run server.ts
```

The server logs `Hypen app streaming on ws://0.0.0.0:3000` and `Web client at http://localhost:3000`. Open http://localhost:3000 in a browser: the server ships a built-in web client that connects back over WebSocket and renders the UI with the DOM renderer. Native clients (Android, desktop) connect to `ws://<host>:3000`. See the [Remote App Tutorial](/docs/getting-started/remote-app) for connecting clients.

The server also logs a warning that no `allowedOrigins`/`authenticate` is configured. That is expected in development; see [Authentication](#authentication) before you deploy.

> **Several modules, none named `App`?** `.app(myApp)` then throws `entry is ambiguous (...)`. Name the entry module `App`, or pick it explicitly with `.module("Counter", def)`.

> **Single-module demo?** You can skip `HypenApp` and pass a definition straight to the server: `new RemoteServer().module("Counter", app.defineState({ count: 0 }).ui(tpl)).listen(3000)`. The module's own template is used when neither `.ui()` nor `.source()` supplies one.

### serve() Helper

For simpler cases, use the `serve()` function:

```typescript
import { app } from "@hypen-space/core";
import { serve } from "@hypen-space/server";

const counter = app
  .defineState({ count: 0 })
  .onAction("increment", ({ state }) => {
    state.count++;
  })
  .build();

await serve({
  module: counter,
  ui: `
    Column {
      Text("Count: @{state.count}")
      Button { Text("+1") }
        .onClick(@actions.increment)
    }
  `,
  port: 3000,
});
```

`serve()` returns the started `RemoteServer`. Its options are `module`, `moduleName` (default `"App"`), `ui`, `source`, `port`, `hostname`, `compression`, `session`, `onConnection` and `onDisconnection`.

## App Builder API

Modules are defined using the chainable `app` builder. Every method returns the builder, so calls can be chained. End the chain with `.build()`, or with `.ui(template)` for a module that carries its own template:

```typescript
import { app } from "@hypen-space/core";

export default app
  .defineState<MyState>(initialState)
  .onCreated(handler)
  .onAction("name", handler)
  .onDestroyed(handler)
  .onError(handler)
  .build();
```

### defineState

Sets the initial state with TypeScript generics for type safety:

```typescript
interface TodoState {
  todos: Array<{ id: string; text: string; done: boolean }>;
  newTodo: string;
  filter: "all" | "active" | "completed";
}

app.defineState<TodoState>({
  todos: [],
  newTodo: "",
  filter: "all",
});
```

### onCreated

Lifecycle hook called when the module is initialized. Receives the state and an optional global context:

```typescript
.onCreated(async (state, context) => {
  // Fetch initial data. Modules run on the server, so use an absolute URL
  // (there is no page origin to resolve "/api/todos" against).
  const response = await fetch("https://api.example.com/todos");
  state.todos = await response.json();

  // Access router for navigation
  if (context?.router) {
    console.log("Current path:", context.router.getCurrentPath());
  }
})
```

### onAction

Registers a handler for a named action. The handler receives a context object:

```typescript
.onAction<PayloadType>("actionName", async ({ action, state, context }) => {
  // action.name     - the action name
  // action.payload  - data from the UI (typed as PayloadType)
  // action.sender   - the component that dispatched the action
  // state           - the current state (mutable, auto-synced)
  // context         - GlobalContext for cross-module access
  // context.router  - HypenRouter for navigation
})
```

Example with typed payload. `action.payload` is optional in the type (a UI can dispatch an action without one), so read it with `?.` or a default:

```typescript
.onAction<{ id: string }>("deleteTodo", ({ action, state }) => {
  state.todos = state.todos.filter(t => t.id !== action.payload?.id);
})
```

### onDestroyed

Lifecycle hook called when the module is unmounted. Use it for cleanup:

```typescript
.onDestroyed((state, context) => {
  clearInterval(state.pollTimer);
})
```

### onError

Catches errors from action handlers and lifecycle hooks. See [Error Handling](/docs/guide/error-handling) for details:

```typescript
.onError(({ error, actionName, lifecycle, state }) => {
  if (actionName) {
    console.error(`Action "${actionName}" failed:`, error.message);
    state.error = error.message;
    return { handled: true }; // suppress error
  }
  // return void for default behavior (log + emit)
})
```

Return values:

| Return | Effect |
|--------|--------|
| `void` | Default: log and emit global error event |
| `{ handled: true }` | Suppress the error |
| `{ rethrow: true }` | Re-throw to the caller |
| `{ retry: true }` | Retry the operation (actions only) |

### build

Finalizes the module definition. `.ui(template)` and `.uiFile(path)` also finalize it, so `.build()` after them is optional. `RemoteServer.module()` and `serve()` build an unbuilt builder for you, but ending the chain explicitly is clearer:

```typescript
const myModule = app
  .defineState({ count: 0 })
  .onAction("increment", ({ state }) => { state.count++; })
  .build();

const ui = `
  Column {
    Text("Count: @{state.count}")
    Button { Text("+") }.onClick(@actions.increment)
  }
`;

new RemoteServer()
  .module("Counter", myModule)
  .ui(ui)
  .listen(3000);
```

## State Management

State uses a Proxy-based system that tracks mutations automatically. Assign values directly and changes propagate to the UI:

```typescript
.onAction<{ name: string; email: string }>("updateProfile", ({ state, action }) => {
  if (!action.payload) return;
  // Direct mutation - tracked automatically
  state.user.name = action.payload.name;
  state.user.email = action.payload.email;

  // Array mutations work too
  state.tags.push("updated");

  // No sync callback needed - changes propagate automatically
})
```

### Deep Nesting

Nested objects are automatically wrapped in proxies:

```typescript
.onAction("setAddress", ({ state, action }) => {
  // Deep nested paths tracked automatically
  state.user.profile.address.city = "New York";
  state.user.profile.address.zip = "10001";
})
```

### Batch Updates

When multiple state changes happen in the same synchronous block, they are coalesced into a single notification via microtask batching. For explicit batching:

```typescript
import { batchStateUpdates } from "@hypen-space/core";

.onAction<Item[]>("bulkUpdate", ({ action, state }) => {
  const newItems = action.payload ?? [];
  batchStateUpdates(state, () => {
    state.items = newItems;
    state.count = newItems.length;
    state.lastUpdated = Date.now();
  });
  // Single notification with all changes
})
```

### State Snapshots

Get a deep clone of the current state. Handlers run on the server, so browser APIs such as `localStorage` are not available; write to a file, a database or an API instead:

```typescript
import { getStateSnapshot } from "@hypen-space/core";

.onAction("save", async ({ state }) => {
  const snapshot = getStateSnapshot(state);
  await Bun.write("backup.json", JSON.stringify(snapshot));
})
```

## Component Patterns

Hypen components pair a `.hypen` template with a TypeScript module. There are four patterns for organizing files:

### Folder-Based (Recommended)

This is the layout `hypen init` creates:

```
src/components/
  App/
    component.hypen    # UI template (the entry, see hypen.json "entry")
    component.ts       # Module logic
  Counter/
    component.hypen
    component.ts
```

A `component.ts` default-exports a definition. The entry is usually unnamed (`app.defineState(...).build()`); child modules are named so templates can mount them and so their actions are routed to them:

```typescript
// src/components/Counter/component.ts
import { app } from "@hypen-space/core";

export default app
  .module("Counter")
  .defineState({ count: 0 })
  .onAction("increment", ({ state }) => { state.count++; })
  .build();
```

### Sibling Files

```
src/components/
  Counter.hypen        # UI template
  Counter.ts           # Module logic
```

Whatever the pattern, the component name comes from the file or folder name. Do not reuse the name of a built-in element (`Badge`, `Card`, `Text`, `Icon`, `Chart`...): built-ins take precedence, so `Badge()` would render the built-in and not your file. Discovery logs a warning when a name collides; use something like `StatusBadge` instead.

### Index Pattern

```
src/components/
  Counter/
    index.hypen        # UI template
    index.ts           # Module logic
```

### Single-File Component

Embed the template directly in TypeScript using the `hypen` tagged template and `.ui()`. Saved as `src/components/Clicker.ts`, it is discovered as `Clicker` and can be mounted from another template as `Clicker()`; its state and actions are scoped to it (as if the template were wrapped in `module Clicker { ... }`):

```typescript
// src/components/Clicker.ts
import { app, hypen } from "@hypen-space/core";

export default app
  .defineState({ count: 0 })
  .onAction("increment", ({ state }) => { state.count++; })
  .ui(hypen`
    Column {
      Text("Count: @{state.count}")
      Button { Text("+") }
        .onClick(@actions.increment)
    }
  `);
```

The `hypen` tag preserves `@{state.*}` and `@{item.*}` expressions as literal bindings instead of interpolating them.

## Component Discovery

Automatically discover components from a directory:

```typescript
import { discoverComponents, loadDiscoveredComponents } from "@hypen-space/server";

// Discover all components
const components = await discoverComponents("./src/components", {
  patterns: ["folder", "sibling", "single-file", "index"], // default: all
  recursive: true,   // default: true
});

// Load them into a usable map
const loaded = await loadDiscoveredComponents(components);
// Map<string, { name, module, template }>
```

### ComponentLoader

A singleton loader for registering and retrieving components:

```typescript
import { resolve } from "node:path";
import { componentLoader } from "@hypen-space/server";

// Register manually
componentLoader.register("Counter", counterModule, counterTemplate);

// Load from directory (pass an absolute path). Picks up all four patterns
// above, recursively, like discoverComponents().
await componentLoader.loadFromComponentsDir(resolve("./src/components"));

// Query
componentLoader.has("Counter");       // true
componentLoader.getNames();           // ["Counter", "App", ...]
const def = componentLoader.get("Counter");
// { name, module, template, path }
```

### File Watching

Watch for component changes during development:

```typescript
import { watchComponents } from "@hypen-space/server";

const watcher = watchComponents("./src/components", {
  onChange: (components) => console.log("Components changed:", components.length),
  onAdd: (component) => console.log("Added:", component.name),
  onRemove: (name) => console.log("Removed:", name),
  onUpdate: (component) => console.log("Updated:", component.name),
});

// Stop watching
watcher.stop();
```

## RemoteServer API

`RemoteServer` streams UI over WebSocket to any Hypen client. It uses a fluent builder pattern; `listen()` returns a promise of the started server:

```typescript
import { RemoteServer } from "@hypen-space/server";

const server = await new RemoteServer()
  .app(myApp)
  .config({ port: 3000, hostname: "0.0.0.0" })
  .session({ ttl: 3600, concurrent: "kick-old" })
  .onConnection((client) => { /* ... */ })
  .onDisconnection((client) => { /* ... */ })
  .listen();
```

### Methods

| Method | Description |
|--------|-------------|
| `.app(hypenApp)` | Register every named module on a `HypenApp` (nested modules, route modules). |
| `.module(name, def)` | Set the entry (primary) module. Optional with `.app()` or `.source()`: the entry is then the module named `App`, or the only module. Accepts a built definition or an unbuilt builder. |
| `.ui(dsl)` | Entry UI template. Optional when the entry module has its own template (`.ui()` on the module) or `.source()` finds one. |
| `.source(dir)` | Discover `.hypen` + module files from a directory (see below). |
| `.config(config)` | Server configuration (see [Configuration](#configuration)). |
| `.session(config)` | Session management configuration. |
| `.onConnection(callback)` | Called when a client's session is ready. |
| `.onDisconnection(callback)` | Called when a client disconnects. |
| `.onSessionCreate(callback)` | Called with each `RemoteSession` as soon as it is created, before the initial render. |
| `.disableAutoRouter()` | Turn off the per-session router that is wired from `Router { Route ... }` blocks. |
| `.exposeStats(enabled?)` | Who may read `/__hypen__/stats` (see [Health & Stats](#health--stats)). |
| `.syncActions()` | Replay every client's actions on every other client's session. |
| `.listen(port?)` | Start the Bun HTTP + WebSocket server. Returns `Promise<this>`. |
| `.prepare()` / `.createSession(transport)` / `.createHandler()` | Host sessions on your own WebSocket stack instead of `listen()`. |
| `.stop()` | Stop the server. |
| `.getClientCount()` | Number of active connections. |
| `.getSessionStats()` | `{ activeSessions, pendingSessions, totalConnections }` |
| `.broadcast(message)` | Send a server message to every connected client. |
| `.url` | `ws://host:port` built from `.config()` while the server is running, else `null`. |

### Component Directory Mode

Instead of passing a UI string, point the server at a components directory laid out as in [Component Patterns](#component-patterns):

```typescript
import { RemoteServer } from "@hypen-space/server";

await new RemoteServer()
  .source("./src/components")  // discovers and loads every component
  .listen(3000);
```

Discovery imports each `component.ts`, so named modules (`app.module("Counter")`) register themselves; `.app()` is not needed. The entry is the component named `App` (or the only one); call `.module("Name", def)` to choose another. `.ui()` is optional because the entry's `.hypen` file supplies the template, and the `Router` blocks in it are wired automatically.

`hypen dev` serves your project in this same mode, from the `components` directory in `hypen.json`.

### Configuration

```typescript
new RemoteServer()
  .config({
    port: 3000,          // default: 3000
    hostname: "0.0.0.0", // default: "0.0.0.0"
    compression: true,   // default: true (permessage-deflate)
    webClient: true,     // default: true, serve the built-in browser client
    allowedOrigins: ["https://app.example.com"], // browser Origin allowlist
    authenticate: (req) => checkToken(req),      // admit or refuse each upgrade
  })
```

| Option | Description |
|--------|-------------|
| `port`, `hostname` | Where `listen()` binds. `listen(port)` overrides `port`. |
| `compression` | Negotiate WebSocket `permessage-deflate`. |
| `webClient` | Serve the built-in web client at `/` (plus the SPA fallback for app routes). `false` serves only the WebSocket and the `/__hypen__/` endpoints. |
| `allowedOrigins` | Exact browser origins allowed to open the WebSocket. Other origins get 403. |
| `authenticate` | `(request) => boolean \| Promise<boolean>`, called before every upgrade. See [Authentication](#authentication). |
| `maxPayloadLength` | Largest accepted WebSocket message in bytes. |

### Compression

Patch streams are JSON, so WebSocket `permessage-deflate` is enabled by
default. It is negotiated per-connection during the upgrade handshake —
clients that don't offer the extension (for example iOS
`URLSessionWebSocketTask`) transparently fall back to uncompressed frames.

Set `compression: false` to opt out, which is handy when you want to read the
raw wire in a proxy or packet capture.

## Session Management

Sessions allow clients to reconnect and restore state after disconnections.

### Session Configuration

```typescript
new RemoteServer()
  .session({
    ttl: 3600,                    // Session TTL in seconds (default: 3600)
    concurrent: "kick-old",       // Concurrent connection policy
    generateId: () => crypto.randomUUID(), // Custom ID generator
  })
```

Concurrent connection policies:

| Policy | Behavior |
|--------|----------|
| `"kick-old"` (default) | New connection replaces existing connection on same session |
| `"reject-new"` | Rejects new connection if one already exists |
| `"allow-multiple"` | Multiple connections share the same session |

### Session Lifecycle Hooks

Register session hooks on the module definition:

```typescript
const myModule = app
  .defineState({ count: 0, draft: "" })

  .onDisconnect(({ state, session }) => {
    // Client disconnected, but session is still alive (within TTL)
    console.log(`Session ${session.id} disconnected`);
    // State is automatically preserved for reconnection
  })

  .onReconnect(({ session, restore }) => {
    // Client reconnected with existing session ID
    console.log(`Session ${session.id} reconnected`);
    // Optionally restore custom state
    restore(savedState);
  })

  .onExpire(({ session }) => {
    // Session TTL expired — no reconnection happened
    console.log(`Session ${session.id} expired`);
    // Clean up any persisted data
  })

  .build();
```

### Session Object

Available in session lifecycle hooks:

```typescript
interface Session {
  id: string;              // Unique session ID
  ttl: number;             // TTL in seconds
  createdAt: Date;         // When the session was created
  lastConnectedAt: Date;   // Last connection time
  props?: Record<string, any>; // Client metadata
}
```

### Connection Flow

1. Client opens WebSocket
2. Client sends a `hello` message with optional `sessionId` to resume
3. Server creates or resumes the session
4. Server sends the initial UI tree as patches
5. Client renders the UI
6. User interactions send `dispatchAction` messages
7. Server processes actions, updates state, streams patches back

## Authentication

Connections are admitted before the WebSocket upgrade, before any session exists. Use `allowedOrigins` to stop other websites from opening sockets from a user's browser, and `authenticate` to check a token, cookie or signed query parameter:

```typescript
new RemoteServer()
  .app(myApp)
  .config({
    allowedOrigins: ["https://app.example.com"],
    authenticate: async (req) => {
      const url = new URL(req.url);
      const token =
        req.headers.get("authorization")?.replace(/^Bearer /, "") ??
        url.searchParams.get("token");
      return token !== null && (await validateToken(token));
    },
  })
  .listen(3000);
```

- `authenticate` runs for every upgrade when it is set. Returning `false` refuses the connection with 403.
- With `allowedOrigins` set, a request whose `Origin` is not listed is refused. Native clients send no `Origin`; they are admitted only when `authenticate` returns `true`.
- With neither option set, every client is admitted and the server logs one warning at startup.

Browsers cannot set headers on a WebSocket, so web clients usually pass a token in the query string or rely on a cookie. Clients can also send metadata in the `props` of their `hello` message; it is available as `session.props`.

## Routing

The `HypenRouter` provides URL-based navigation:

```typescript
import { HypenRouter } from "@hypen-space/core";

const router = new HypenRouter();

// Navigation
router.push("/users/123");
router.replace("/login");
router.back();
router.forward();

// Current route
router.getCurrentPath();                    // "/users/123"
router.getParams();                         // { id: "123" }
router.getQuery();                          // { tab: "posts" }
router.isActive("/users/:id");              // true

// Pattern matching
router.matchPath("/users/:id", "/users/42");
// { params: { id: "42" }, query: {}, path: "/users/42" }

// Listen for changes
const unsubscribe = router.onNavigate((state) => {
  console.log(`Navigated to ${state.currentPath}`);
});
```

Use the router in action handlers via `context.router`:

```typescript
.onAction("login", async ({ state, context }) => {
  const success = await authenticate(state.email, state.password);
  if (success) {
    context.router?.push("/dashboard");
  }
})
```

### Auto-wire + `@router.*`

`RemoteServer` auto-discovers every `Router { Route ... }` block in
the primary template (and any child component template) at session
start and spins up a per-session `ManagedRouter`. You don't wire it
yourself. DSL authors dispatch the reserved namespace:

```hypen
Button { Text("Search") }.onClick(@router.push, to: "/search")
Button { Text("←") }.onClick(@router.back)
```

The session mirrors the current path into primary `state.location`
automatically when the primary's state shape carries that field. The
built-in web client keeps the browser URL in sync with `state.location`:
in-app navigation pushes a history entry, back/forward navigate, and
opening or reloading a deep link such as `/counter` starts on that route.

`@actions.*` are scoped to the module whose template uses them, so a
child module cannot call its parent's action. Navigate with
`@router.push` (or `context.router?.push()` in a handler) rather than a
`navigate` action on the root module.

Per-route modules load data in `onActivated` by reading route
params off the router:

```typescript
app.module("UserProfile")
  .defineState<{ user: User | null }>({ user: null })
  .onActivated(async (state, ctx) => {
    const m = ctx?.router?.matchPath("/users/:id", ctx.router.getCurrentPath());
    const id = m?.params.id;
    if (id) state.user = await fetchUser(id);
  })
  .build();
```

Nested `Router` blocks inside child components flatten into the same
route table — see the [Routing Guide](/docs/guide/routing) for the
full semantics (first-seen dedup, shared URL space). Opt out with
`server.disableAutoRouter()` to wire routing manually in an
`onSessionCreate` hook.

## Global Context

Cross-module communication uses the `HypenGlobalContext`:

```typescript
import { HypenGlobalContext } from "@hypen-space/core";

const globalContext = new HypenGlobalContext();

// Access other modules
const auth = globalContext.getModule<AuthState>("auth");
auth.state.isLoggedIn;
auth.setState({ token: "abc" });

// Event bus
globalContext.emit("userLoggedIn", { userId: "123" });
const unsub = globalContext.on("userLoggedIn", (payload) => {
  console.log("User logged in:", payload);
});

// Query
globalContext.hasModule("auth");       // true
globalContext.getModuleIds();           // ["auth", "counter"]
globalContext.getGlobalState();         // combined state snapshot
```

### Typed Events

For type-safe event handling, describe your events with a `type` alias. `TypedEventEmitter` needs a map that is assignable to `Record<string, unknown>`, which an `interface` is not, so `interface AppEvents { ... }` fails to type-check.

```typescript
import { TypedEventEmitter } from "@hypen-space/core";

type AppEvents = {
  "user:login": { userId: string; email: string };
  "user:logout": { userId: string };
  notification: { message: string; type: "info" | "error" };
};

const events = new TypedEventEmitter<AppEvents>();

events.on("user:login", (payload) => {
  // payload is typed as { userId: string; email: string }
  console.log(`${payload.email} logged in`);
});

events.emit("user:login", { userId: "1", email: "alice@example.com" });
```

### Framework Events

`HypenFrameworkEvents` (exported as a type) declares the event names the framework reserves:

| Event | Payload |
|-------|---------|
| `module:created` | `{ moduleId }` |
| `module:destroyed` | `{ moduleId }` |
| `route:changed` | `{ from, to }` |
| `state:updated` | `{ moduleId, paths }` |
| `action:dispatched` | `{ moduleId, actionName, payload? }` |
| `error` | `{ message, error?, context? }` |

Today the runtime emits only `error` (when a handler throws and `onError` does not handle it). The others are reserved names; for route changes use `router.onNavigate()`.

## Logging

Configure logging for debugging:

```typescript
import { setLogLevel, setDebugMode, configureLogger } from "@hypen-space/core";

// Set global log level
setLogLevel("debug");    // "debug" | "info" | "warn" | "error" | "none"

// Shortcut: true = "debug", false = "error"
setDebugMode(true);

// Full configuration. The handler is an object with one method per level.
configureLogger({
  level: "info",
  timestamps: true,
  colors: false,
  handler: {
    debug: (tag, ...args) => console.debug(`[${tag}]`, ...args),
    info: (tag, ...args) => console.info(`[${tag}]`, ...args),
    warn: (tag, ...args) => console.warn(`[${tag}]`, ...args),
    error: (tag, ...args) => console.error(`[${tag}]`, ...args),
  },
});
```

Default levels: `info` in development, `warn` under test runners (`NODE_ENV=test`, which `bun test` sets), `error` with `NODE_ENV=production`.

### DEBUG namespaces

Set `DEBUG` to add the `debug` level for chosen loggers, as with the `debug` package. It only adds output: a matching logger prints every level, even when the global level is higher (`NODE_ENV=production` or `test`), and every other logger keeps the global level. Without `DEBUG`, `info`, `warn` and `error` messages already print in development.

```bash
DEBUG=hypen:* bun run server.ts               # debug output from all Hypen loggers
DEBUG=hypen:remote,hypen:router bun run server.ts
DEBUG=hypen:*,-hypen:state bun run server.ts  # debug output from all but State
```

An excluded namespace (`-hypen:state`) is only left out of the extra `debug` output; its `info`, `warn` and `error` messages still print at the default level. To quiet a logger, raise the global level with `setLogLevel()`.

Namespaces are `hypen:` plus the lower-cased logger tag (`hypen:remote`, `hypen:engine`, `hypen:router`, `hypen:state`, `hypen:module`, `hypen:loader`, `hypen:renderer`, ...); a namespace also covers its children. In a browser, set `localStorage.debug = "hypen:*"` and reload. From code, call `setDebugNamespaces(spec)` from `@hypen-space/core/logger`. `DEBUG` has no effect when the level is `"none"`. Under the CLI, `DEBUG=hypen:* hypen dev` is the same as `hypen dev --debug`.

<Callout type="warn">
`DEBUG` namespaces need `@hypen-space/core` 0.6.7 or newer; older versions ignore `DEBUG`.
</Callout>

### Loggers

Framework subsystems have individual loggers, and `createLogger(tag)` makes your own:

```typescript
import { frameworkLoggers, createLogger } from "@hypen-space/core";

// frameworkLoggers: hypen, engine, router, state, events, remote, renderer,
// module, lifecycle, loader, context, discovery, plugin, canvas, debug
frameworkLoggers.remote.info("custom message");

const log = createLogger("Billing");
log.info("invoice sent");          // prints at the default "info" level
log.debug("payload", { id: 42 });  // prints only with DEBUG=hypen:billing (or level "debug")
```

## Testing

Test modules without a running server. A built definition keeps its action handlers in `handlers.onAction`, a `Map` from action name to handler (`actions` is only the list of names):

```typescript
import { test, expect } from "bun:test";
import { app } from "@hypen-space/core";

const counterDef = app
  .defineState({ count: 0 })
  .onAction<{ by?: number }>("increment", ({ action, state }) => {
    state.count += action.payload?.by ?? 1;
  })
  .build();

test("increment increases count", async () => {
  const state = { count: 0 };

  // Call the action handler directly
  const increment = counterDef.handlers.onAction.get("increment")!;
  await increment({
    action: { name: "increment", payload: { by: 2 } },
    state,
    context: null as any, // not used by this handler
    dataSources: {},
  });

  expect(state.count).toBe(2);
  expect(counterDef.actions).toEqual(["increment"]);
});
```

### Testing with HypenModuleInstance

For integration tests with the full module lifecycle, run the definition on a real engine. This file stands on its own (save it as, say, `counter.lifecycle.test.ts` and run `bun test`):

```typescript
import { test, expect } from "bun:test";
import { app, HypenModuleInstance } from "@hypen-space/core";
import { Engine } from "@hypen-space/server";

const counterDef = app
  .defineState({ count: 0 })
  .onAction<{ by?: number }>("increment", ({ action, state }) => {
    state.count += action.payload?.by ?? 1;
  })
  .build();

test("module lifecycle", async () => {
  const engine = new Engine();
  await engine.init();

  const instance = new HypenModuleInstance(engine, counterDef);
  const state = instance.getLiveState();

  expect(state.count).toBe(0);

  // Dispatch action through the engine
  engine.dispatchAction("increment");
  expect(state.count).toBe(1);

  await instance.destroy();
});
```

## Health & Stats

Internal HTTP endpoints live under the reserved `/__hypen__/` prefix, so app routes such as `/stats` or `/health` stay free:

- **`GET /__hypen__/health`**: `{"status":"ok","server":"hypen-remote"}`, for load balancer checks.
- **`GET /__hypen__/stats`**: `{ activeSessions, pendingSessions, totalConnections }`. Private by default: only direct loopback requests get it (requests with `Forwarded`, `X-Forwarded-For` or `X-Real-IP` count as remote); everyone else gets a 404. `.exposeStats()` serves it to every client (restrict `/__hypen__/` at your proxy), and `.exposeStats(false)` turns it off.

The legacy `GET /health` (plain `OK`) and `GET /stats` still answer requests that don't ask for HTML, for existing probes. A browser navigating to `/health` or `/stats` gets the app instead.

With the built-in web client on, any other `GET` page navigation (accepting `text/html`, outside `/__hypen__/`, with no file extension) gets the app's HTML shell, so deep links work. Unknown asset paths get a 404.

```typescript
const server = await new RemoteServer()
  .module("App", appModule)
  .ui(ui)
  .listen(3000);

// Programmatic access
server.getClientCount();     // number of active connections
server.getSessionStats();    // { activeSessions, pendingSessions, totalConnections }
```

## Deployment

Deploy your server to any platform that runs Bun and supports WebSockets. Read the port from the environment:

```typescript
await new RemoteServer()
  .source("./src/components")
  .listen(Number(process.env.PORT ?? 3000));
```

### Docker

```dockerfile
FROM oven/bun:1
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --production
COPY . .
EXPOSE 3000
CMD ["bun", "run", "server.ts"]
```

The same image works on Fly.io, Railway, Render and other container hosts; point their health check at `/__hypen__/health`.

> A `hypen init` project can also be deployed as a static site: `hypen build` writes a self-contained `dist/` (including `dist/server.js`, a zero-dependency static server) that runs your modules in a Web Worker in the browser. Use `RemoteServer` when modules must run on your server (secrets, databases) or when native clients connect.

### Production Checklist

- Set `allowedOrigins` and/or `authenticate` (the startup warning then goes away)
- Set appropriate session TTL for your use case
- Use `/__hypen__/health` for load balancer checks
- Monitor active connections via `getSessionStats()` (or `/__hypen__/stats` from the same host)
- Each client gets its own module instance; plan memory accordingly
- Consider `concurrent: "kick-old"` (default) to prevent stale connections
